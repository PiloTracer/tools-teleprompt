# Pairing API — Feature SPEC

**Status:** Draft  
**Owner:** eng  
**ADRs referenced:** 002, 003, 004  
**Related plans:** foundation scope FR-05, FR-08; initial scope Flow B

---

## 1. Purpose

Ephemeral HTTP API for cross-device script relay: desktop creates session, mobile claims with OTP, server deletes payload immediately. No user accounts, no durable storage.

---

## 2. In scope / Out of scope

**In scope:**

- `POST /api/v1/sessions` — create session
- `POST /api/v1/sessions/{token}/claim` — verify OTP, return script once
- Background expiry (Redis TTL + optional sweep)
- Rate limiting per IP
- Health check `GET /health`

**Out of scope:**

- QR fragment handoff (client-only)
- File uploads (JSON text body only)
- Authentication / API keys for users
- Script library or listing endpoints

---

## 3. Domain language

| Term | Definition |
|------|------------|
| Session | Ephemeral pairing record in Redis |
| Token | Unguessable path segment (128-bit) |
| OTP | 6-digit one-time code shown on desktop |
| Claim | Successful OTP verification + payload delivery |

---

## 4. Behavioural spec

- **R1.** Create accepts JSON `{ "text": string, "format": "plain" | "markdown" }`; validates UTF-8 and max size (default 256 KB).
- **R2.** Create returns `{ "token", "otp", "claim_url", "expires_at" }`; OTP shown once to desktop client; store **otp_hash** (bcrypt or HMAC-SHA256) in Redis, never plaintext OTP at rest after response if avoidable (hash immediately).
- **R3.** Token entropy ≥ 128 bits from CSPRNG; URL-safe encoding.
- **R4.** Redis key TTL = 300 seconds on create; key pattern `pairing:session:{token}`.
- **R5.** Claim accepts JSON `{ "otp": string }`; constant-time compare against hash.
- **R6.** On successful claim: return `{ "text", "format" }` once; **delete** Redis key atomically.
- **R7.** Failed OTP increments attempt counter; lock session after **5** failures (return 423 Locked).
- **R8.** Second claim on same token returns **410 Gone** with no body.
- **R9.** Expired session returns **404** on claim.
- **R10.** Rate limit: max **10** creates and **20** claims per IP per 15 minutes (configurable).
- **R11.** Logs record event type only; never log `text`, `otp`, or full `token`.

---

## 5. Data model

**Redis value (JSON serialized):**

```json
{
  "otp_hash": "...",
  "attempt_count": 0,
  "text": "...",
  "format": "plain|markdown",
  "created_at": "ISO-8601"
}
```

No SQL schema.

---

## 6. APIs

| Method | Path | Request | Success | Errors |
|--------|------|---------|---------|--------|
| POST | `/api/v1/sessions` | `{ text, format? }` | 201 + session meta | 413, 429, 400 |
| POST | `/api/v1/sessions/{token}/claim` | `{ otp }` | 200 `{ text, format }` | 404, 410, 423, 429, 400 |
| GET | `/health` | — | 200 `{ "status": "ok" }` | 503 if Redis down |

Problem Details (RFC 7807) for errors.

---

## 7. Invariants

- **I1.** At most one successful claim per session.
- **I2.** No script text in Redis after successful claim or TTL expiry.

---

## 8. Error model

| status | type | When |
|--------|------|------|
| 413 | payload-too-large | text over limit |
| 429 | rate-limit | IP exceeded |
| 423 | locked | OTP attempts exhausted |

## 10. Security and privacy

- Sensitive: script text in Redis ≤5 min only.
- Threat: token guessing → mitigated by entropy + OTP + TTL.
- Threat: abuse → rate limits + max size.
- Redis on internal Docker network only.

| R11 | log capture asserts no script in output |

## 12. Rollout and rollback

Deploy `api` container with Redis dependency. Rollback: drain traffic; TTL clears sessions automatically.
